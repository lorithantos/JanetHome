
pattern.change-coalescing
  State belongs in structure, not in bookkeeping that describes it. Two instances of one move. (1) Coalescing input changes into output work: key partitions, queue buffers, DESTINATION collapses -- the fold belongs to the consumer, so two consumers fold the same stream differently and a complete list can be folded non-associatively. A consumer loop waits for non-empty, delays one frame, drains GREEDILY to empty (stragglers make the current frame), awaits delivery; the loop position IS the window, so no armed flag, no race, no overlapping deliveries, backpressure free. Output rate capped at one per window by construction, so a fast producer can never overwhelm it -- only a slow consumer can. Plus laziness: per-output cells, never a base class. (2) Capping simultaneous calls to a remote (N items, K slots) -- the question people arrive with. Cold answers stop at SemaphoreSlim because it is CORRECT, and every weakness is second-order: leaked permits, nowhere for results or retry, K cannot change, no ordering. Better: K worker loops (K loops IS the limit), or a K-slot list where WhenAny is a wake-up to discard and you sweep for completed slots -- the slot index is the identity. The slot list has a coordinator, which buys unsynchronized results, per-item retry, adaptive K on 429s, and deterministic start order. Chunking is worse (a barrier that turns one poison pill into a total stall, and retry re-runs survivors) UNLESS the batch is the request -- "K at a time" means K per call or K in flight, and they want opposite structures. Concurrency cap is not a rate cap. The portable tell: when correctness depends on a paired acquire and release, there is usually a version where the thing is not a resource at all.
  notes\coalescing-input-to-output.md
  ! First implementation shipped 2026-08-08 in RetirementCore (RetirementCore.App\Coalescing: ChangeCoalescer, Derived<T>, AsyncDerived<T>, deterministic pump+fake-clock test harness). The machine survived contact; the async-cell addition it forced (two counters, staleness independent of status) is recorded in the note.
  ! The request/response variant (batching loader / dataloader shape) is specified only as a contrast table; correlation and failure fan-out are unbuilt and are a genuine extension, not a free consequence.

pattern.discriminator-backends
  Split conditional tangles that are really dispatch: a discriminator front end that only routes, over a catalog of well-known fixed back ends (state machines as declarative queries) that only compute. Duplication corollary: copies behind a discriminator are enumerable inventory, not silently-drifting contraband - deliberately anti-DRY-reflex. RazorGraph-era tooling upgrades it: method_body_diff proves which back ends are merge candidates, coverage prices refactor risk upfront, and conformance (every path lands in exactly one back end, nothing routes around the front end) is a graph query. The tell: a method whose nesting grows every time the business adds a case.
