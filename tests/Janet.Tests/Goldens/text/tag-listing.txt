note.census-the-population
  Census the population; the anomaly announces itself. When one instance will not explain itself, classify every instance you can reach and sort by frequency -- over-representation is counted, not deduced, and needs no theory of the bug. Corollaries: the classifier must be a marker present on EVERY member (the byproduct nobody can turn off), and absence is a finding (a count of zero is invisible to instance inspection). Origin: a WinINet leak found by running a per-object vtable type-recovery extension across the whole heap and tallying -- thousands of copies of one structure, turning "memory is growing" into a type name and therefore an owner; the vfptr is the only self-describing marker in a native C++ heap, which managed devs later got as !dumpheap -stat. WHEN: memory growth with no obvious owner, a dump that will not explain itself, a query returning suspiciously empty results, any "I do not know what I am looking for" moment -- count first, inspect second.
  notes\census-the-population.md
  ! The census is only as honest as its classifier: a marker that non-polymorphic types (or unextracted node kinds) lack will undercount silently, which produces the absence-as-finding trap in reverse -- a zero that means "not classifiable" rather than "not there". State what the classifier can see.

note.janet-mcp-port
  The C# catalog port and its cutover. Janet.Core holds the logic; janet (CLI) and janet-mcp (stdio + HTTP) are thin front ends, both .NET global tools so client config is a bare command name. HTTP transport is the point of the design: an HTTP server is a separate process the client dials, so it survives being killed and rebuilt mid-session (Claude Code reconnects with five-attempt backoff), while a stdio server is a child the client holds open and is never reconnected -- which is why RazorGraph needs a publish-and-restart per change. Query and splice writer are ported with byte-identical output to the PowerShell, proven by 41 tests. Staging: research.json stays under the scripts, research.candidate.json is the only thing the port writes, and research.candidate.base.json is the frozen common ancestor the cutover diffs against.
  notes\janet-mcp-port.md
  ! Writes default to research.candidate.json, NOT the live graph, while the candidate exists. Targeting the live file needs an explicit --graph research.json. One forgotten flag would merge the two sides and destroy the delta arithmetic the cutover depends on; the default retires itself once the swap removes the candidate.
  ! A stale installed tool silently ignores that default. The .nupkg is built from source at pack time, so changing GraphLocator and forgetting to repack leaves the global tool on the old behaviour -- it wrote two nodes into the live graph that way. dotnet tool update no-ops on an identical version: uninstall and install, or bump the version.
  ! research.candidate.base.json is load-bearing and easy to omit: the seed hash can only say THAT the live graph moved, not WHICH nodes moved, and integrating them forward is a three-way comparison. The first cut of the plan stored only a hash and was not implementable.
  ! Add-ResearchNode.ps1 and Update-ResearchNode.ps1 disagree on field order (add: tags before caveats; update: caveats before tags). Both are reproduced verbatim for parity, so a node added by one path and later touched by the other gets its fields reordered -- a whole-node diff through the back door. Unsettled.
  ! Neither implementation can DELETE a node. Update -Remove drops a field, not a node. Removing one means restoring the file, which is why a stray sandbox write is expensive rather than trivial to undo, and why Swap-ResearchGraph.ps1 refuses rather than stripping them for you.
  ! Still unported: research rename, thread items, API/assembly introspection, dotnet check, the shim pass, and the documentation pass. janet does not write the research trace Invoke-ResearchGuard.ps1 reads, so the shim must keep writing it or the guard silently stops firing at cutover.
  ! MEASURED, not inferred: over HTTP a rotation hot-swaps tool BEHAVIOUR but not the tool SURFACE. An attached session reconnects to the new process and calls run the new code (verified across pids 25960 -> 37248 -> 2996 -> 38192 -> 9736, no session restart, ~1.9s per rotation), while tool descriptions and schemas stay as fetched at connection time. Firing NotificationMethods.ToolListChangedNotification from inside a tool did NOT clear it -- the notification was observed on the response stream and the surface still did not refresh. So: behaviour changes are free, signature/description/add/remove changes need a session restart. Over stdio nothing swaps at all; killing the server just removes the tools, with no respawn.
  ! MEASURED, the full picture: over HTTP a rotation swaps tool BEHAVIOUR and ARGUMENTS live, but not the tool LIST. Attached sessions reconnect to the new process and run new code with no restart (~1.9s per rotation). A NEW PARAMETER on an existing tool works immediately -- the client forwards arguments without validating them against its cached schema, verified by adding a 'probe' parameter and having an attached session call it successfully. A NEW TOOL does not: research_ping existed on the server and was invisible to the attached session. Descriptions stay as fetched at connection time. tools/list_changed does not help and was tried twice -- from inside a tool call, and pushed out of band via RunSessionHandler three seconds after session establishment (the server logged the push; nothing refreshed). So a client's tool LIST is fixed at connect and nothing the server says changes it. Practical rule: change logic and add parameters freely mid-session; adding or removing a TOOL, or wanting an updated description, needs a session restart.
  ! CORRECTION to the caveat above, which was wrong: a NEW TOOL *does* become usable mid-session over HTTP. research_rename was added, rotated in, and then invoked successfully from the already-running session -- schema and all. The earlier 'new tools are invisible' result came from checking too early: reconnection is LAZY, happening on the next MCP call rather than when the server restarts, and the research_ping test ran a tool-list search immediately after a rotation without making any call in between, so it read the client's pre-rotation list. Not-yet was recorded as never. Practical rule: rotate, then MAKE A CALL, then look -- the surface catches up on reconnect. Still genuinely unresolved: tool DESCRIPTIONS looked stale even after a reconnect, so names and descriptions may refresh on different schedules, or the refresh may simply be asynchronous and the checks kept beating it. Do not trust either direction without re-testing with a deliberate call in between.

note.razorgraph-mcp-server
  MCP stdio server over the RazorGraphTool code graph (D:\Repos\RazorGraphTool\src\RazorGraph.Mcp) - the DESIGN-NOTES section-4 graph-first pattern rebuilt clean-room; 22 tools (exception_escapes added 2026-08-07), Janet JSON envelope conventions. Holds many graphs at once (keyed registry, optional graphId on every tool). build_solution spans a whole solution so Calls/InjectedInto cross project boundaries, and emits Covers edges from test methods to the code they exercise (full call closure, depth carried on each edge); excludeTests=true skips test projects before compiling for a lean navigation graph. Method-level detail: explicit constructors are Method nodes, using/await-using disposal is a Calls edge, bodyDepth nesting metric feeds deep_methods (the christmas-tree report), method_body_graph exposes one method's CFG with guard depths, method_body_diff proves two bodies flow-equivalent by bisimulation. Member-level detail since cd12114 (2026-08-08): Property and Field nodes (statics included, isStatic/isConst marked), Reads/Writes edges from the accessing code, References edges to member declared types. Generated code (f97edee): #line-mapped positions, generated:true markers, generatedFrom on Razor-generated classes, page->class join via References+compiledInto. Traversal takes a direction (outgoing/incoming/both) and descends containment for free.
  notes\razorgraph-mcp-server.md
  ! build_graph and build_solution are slow (full Roslyn compile); build_solution compiles every project in the solution. Solution graphs scope Razor and client-asset ids by project name (page:<Project>/<relPath>, js:<Project>/<relPath>), so ids differ from single-project graphs of the same code.
  ! .mcp.json launches a PUBLISHED copy -- D:/Repos/RazorGraphTool/.mcp-bin/RazorGraph.Mcp.exe, absolute path, gitignored -- refreshed with: dotnet publish src\RazorGraph.Mcp -c Release -o .mcp-bin. It used to launch the live bin/Debug output, which a running server locks, so any rebuild of that configuration failed with MSB3021 while a Claude session was up. Verified 2026-08-01 that Debug and Release solution builds both succeed with the server live. Residual: .mcp-bin itself is locked while a session runs, so re-publishing needs those sessions closed, and code changes reach the MCP tools only after re-publish AND a session restart.
  ! Covers edges are call-graph reachability to the FULL call closure (since 73ddf10, 2026-08-02; was depth 3), not runtime coverage - a covered method is one some test can reach, not one a test asserted on. Each edge carries the depth it was reached at; filter on depth for direct exercise. Traversal seeds from the test and from its class lifecycle hooks and constructor. uncovered_methods excludes bodiless interface/abstract declarations. Since 20ff394 coverage queries HARD-ERROR on a graph containing zero test methods (single-project builds, excludeTests builds) instead of returning empty - everything-uncovered was the absence-as-finding trap.
  ! Roslyn injection heuristic misclassifies positional-record constructor parameters as injectedServices (ConversionQueueStatus in ImageSelectorV2 lists int/long/List<string> as "services"). Needs a record/primitive exclusion. Still present as of 2026-08-08; the planned attribute-driven DI detection would fix it as a side effect.
  ! Type-usage edges are PARTIAL: since cd12114 (2026-08-08) property/field declared types emit References edges (unwrapping List<>/array wrappers), so "who uses this type" IS answerable for member-typed usage. Return types and parameter types still carry no edges - a type used only in method signatures still shows nothing.
  ! Saved-graph JSON field names differ from the in-memory model: edges serialize as from/to (not fromId/toId), node ids carry kind prefixes (type:, svc:, ctrl:, m:, prop:, field:, page:, js:). Hand-written blob queries against the wrong names return empty and look like "no edges" - verify against the orientation view (Search-Json.ps1) first.
  ! The published .mcp-bin predates ALL 2026-08-08 work until re-published: exception_escapes (2026-08-07), member extraction (cd12114), --no-tests + coverage guard (20ff394), generated-code marking/mapping/links (f97edee). Publish loop: close sessions -> dotnet publish both projects -> restart. The CLI twin sees everything immediately. The OLD server CAN load_graph new CLI-built graphs - every enum name pre-exists, and the page->class join deliberately rides References+compiledInto=true instead of a new EdgeType because JsonStringEnumConverter throws on unknown names.
  ! Zero-Property-node gap RESOLVED IN SOURCE at cd12114 (2026-08-08); verified on RazorGraphTool self-graph and ImageSelectorV2 (the ConversionQueueStatus zero-edge case now answers). Graphs built by the published server, and ANY saved graph predating cd12114, still contain zero Property/Field nodes - date-check a saved graph before trusting an empty incoming list.
  ! Writes detection is assignment-syntax only (=, compound, ++/--, out/ref): mutating a member through a method call reads it - list.Add(x), dict.TryAdd(k,v) yield a Reads edge on the member plus a Calls edge to the (usually out-of-solution) mutator. Found self-graphing 2026-08-08. Honest about syntax, blind to semantic mutation - do not read an absent Writes edge on a collection-typed member as immutability.
  ! Escape reports cite the thrower METHOD node, not the throw site: a throw authored in a .cshtml code block whose enclosing method is generated scaffolding (ExecuteAsync) still displays the .g.cs path even after f97edee - the node is correctly marked generated:true with generatedFrom and a compiledInto edge back to the page, but the mapped .cshtml line of the throw itself is not persisted on the edge. Persisting throw-site locations is the open follow-up.

script.get-api-doc
  Queries a .NET XML documentation file the way Get-Research queries research.json: ranked free-text search returning parsed members (kind, declaring type, readable signature, summary, per-parameter docs) instead of grep hits. Exists because researching a library from raw doc XML is expensive and bad at the job -- the file is one stream of hard-wrapped indented <member> elements, so a match costs dozens of context lines and the answer arrives split across them. Flattens doc markup (see cref, paramref, c) into prose, shortens fully-qualified argument lists, and follows <inheritdoc/> chains transitively (BarSeries -> Series -> ISeries is the ordinary shape, and one hop makes results depend on document order). Resolves the .xml from the NuGet cache by package id, newest version and newest TFM, so callers never hunt for the path. JSON by default with the standard envelope; -Text to read at a terminal; -Package alone gives cheap orientation (counts by kind, largest types).
  scripts\Get-ApiDoc.ps1
  ! A bare <inheritdoc/> with no cref is NOT resolved -- implicit inheritance needs the type hierarchy, which an XML doc file does not carry. Those members read as undocumented even though the base or interface documents them; check the base type by name when a result looks empty.
  ! Only reads XML that ships inside the package under lib\<tfm>\. Packages built without GenerateDocumentationFile throw a clear error rather than returning nothing, and a package documenting only some members will honestly report the rest as undocumented.
  ! Generic arity survives in names as it does in the file (Series`3, CoreAxis`2), so query by simple name rather than pasting a C# generic.

script.get-research
  Queries research.json by id, tag, kind, or scored free text, returning a ranked top-N shortlist; the single retrieval entry point so startup never loads the full inventory.
  scripts\Get-Research.ps1
  ! -Text is denser than the JSON for multi-node results (75% of the size: it drops the per-node field names), so it is the cheaper form for a model scanning a shortlist -- the opposite of Invoke-JanetStartup, where -Text is 251% because it adds every rule why. Choose by what the projection contains, not the flag name. -Text is written with Write-Host, so it cannot be captured by pipe, > redirection, or assignment; use 6>&1. See note.startup-brief-budget.

script.invoke-research-guard
  PreToolUse hook enforcing RESEARCH FIRST: writing a NEW .ps1 into a scripts directory is denied unless Get-Research.ps1 has run recently. The denial is not a nag -- it runs the catalog query itself on terms taken from the file name and hands back the closest existing nodes, so the answer arrives with the block. Clearing it is one command, which is the command that should have been run. Written 2026-08-11 after Get-AssemblyApi.ps1 was authored while script.get-api-doc already answered the same question; nothing was violated, because the manifest explained HOW to query the catalog and never said TO. Deliberately narrow: creation only, .ps1 only, scripts/ only -- the moment a duplicate tool becomes permanent is when it is authored, and a guard that fires on everything gets clicked past. Get-Research.ps1 leaves the trace (-NoTrace suppresses it, used by the guard's own lookup so it cannot clear the check it is about to make). Graph-first is a technique for once you know what you are building; this ranks above it.
  scripts/Invoke-ResearchGuard.ps1
  ! Wired in TWO places and needs both: .claude/settings.json arms it when the project dir is JanetHome, and ~/.claude/settings.json arms it by absolute path everywhere else. The failure that motivated it happened while the project dir was a DIFFERENT repo, so project-level wiring alone would not have caught it.
  ! The trace is one file in the temp directory, so concurrent sessions share it -- one session's query clears another's guard. Accepted, not solved: the check is a prompt to think, not a security boundary.
  ! Fires only on Write of a new .ps1 directly inside a folder named 'scripts'. Notes, source files, and edits to existing scripts pass untouched.

script.search-json
  Generic JSON-blob search with Get-Research conventions: orientation view (arrays + field census), scored -Query, prop=value -Where filters with wildcards and dotted paths, -Select projection, { returned, totalMatches, truncated, items } envelope, -Text opt-in. Built 2026-08-01 for querying saved RazorGraph graphs without the MCP server; works on any JSON file whose interesting content is an array of objects.
  scripts\Search-Json.ps1
  ! Loads the whole file into memory (fine for MB-scale graphs). Unlike Get-Research it caps -Where results too (default -First 10) because blob arrays can hold tens of thousands of items; -All lifts the cap and the envelope always says when it was applied.

script.update-research-node
  Updates an existing research.json node in place with validation; preserves unknown fields and splices textually so the file keeps its curation.
  scripts\Update-ResearchNode.ps1
